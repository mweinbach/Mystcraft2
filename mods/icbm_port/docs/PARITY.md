# ICBM Classic parity audit

Target: Minecraft 1.19.2, Fabric, Java 17. Reference: BuiltBrokenModding/ICBM-Classic `prod/1.12` commit `9c1d985a375adc2868ff47707b3a636452d0b63a`. Audit date: 2026-10-19 (alpha.4).

This is a source and behavior migration audit of the **current working tree**, not a declaration of complete recreation. **Missing** means no implementation found; **approximation** means usable but materially different behavior; **partial** means a subset of upstream behavior. **Verified** requires evidence of a match to the specific acceptance criteria. No subsystem below has a full-parity verification claim.

The alpha.4 local build, 92 gameplay GameTests (the suite at that time) plus the isolated five-reload material test, 16 JUnit tests and resource validation passed. The current tree runs **108 gameplay GameTests** (including the opt-in extreme-payload benchmark), the material test and 21 JUnit tests; see [VALIDATION.md](VALIDATION.md). Alpha.4 full-pack Tekxit client/world startup, all six integration cases and live EMI index checks passed before and after reload. Redmatter consumption/core animation and defense hardware were inspected directly. The historical alpha.3 full Tekxit 4 client passed six actual-provider integration tests and native EMI index checks before and after reload. A prior client session with JEI loaded a creative world and displayed dynamic held-item recipes. See [VALIDATION.md](VALIDATION.md) for checks and limits. These results do not verify every upstream mechanic or multiplayer presentation. The inventory [upstream-inventory.json](upstream-inventory.json) records 660 production Java paths, 467 resource paths, 130 recipe/factory paths, 27 explosive definitions and field names in 42 config files. The inventory records upstream symbols and paths only; implementation status is maintained in the tables here.

## GUI, networking, radio and energy

Five upstream screens/containers exist under `content/blocks/`: launcher base, launcher screen, cruise launcher, radar station and EMP tower (`*/gui/`). The launcher screen/container is implemented; cruise and tiered launchers share that adapted screen. Radar/EMP/SAM now have their own server-backed shared machine screen; separate upstream layouts/graphics remain adapted. Acceptance requires matching meaningful controls and displayed state, slots/shift-click, battery slot handling, energy bars, target/channel fields, launch/disable/redstone/rotation actions, range/error feedback and multiplayer live updates. Original screen art/layout must be independently recreated.

Network sources: `lib/network/` (packet events/manager, entity and tile lambda/codex packets, player-item packet, entity position, air particles and block explosion) and machine/entity packet handlers. Current status: partial. Validated Fabric launcher configuration packets, projectile tracking and custom guided-SAM spawn tracking exist; the complete upstream packet/effect system is absent. Fabric replacements must validate sender, dimension, loaded target, distance, current screen, slot access, enum/range bounds, payload length and permissions; execute world edits on the server thread and reject invalid actions. Test two clients, forged coordinates, stale blocks, chunk unload and unauthorized remote updates. Registering packet IDs alone is insufficient.

Radio sources: `api/radio/`, `lib/radio/`, `content/blocks/radarstation/RadioRadar.java`. Current status: paired launcher remote plus `radio/RadioNetwork` channel registry, incoming-target messages and bounded relays; full upstream message vocabulary absent. Test dimension/channel registry lifecycle, sender/receiver discovery, channel access, text/target/incoming-missile/trigger messages, machine forwarding and reload cleanup. A radius search for blocks without the message contract is an approximation.

Energy sources: `api/energy/`, `lib/energy/`, `content/blocks/launcher/network/NetworkEnergyStorage.java`, `content/items/ItemBattery.java`. Current status: configurable battery and machine buffers exposed through TeamReborn transactional Fabric energy, plus supported charging paths; Forge FE ABI absent. Upstream has FE and null systems and configurable power requirement. Fabric replacement must document chosen units/API, capacities/input/output, simulate versus commit, side restrictions, network distribution, battery transfer and action costs. No built-in energy API replacement can be called Forge Energy compatibility without a tested bridge.

## Recipes, progression and configuration

All **130** reference recipe/factory paths are enumerated individually in the inventory, including conditional alternatives. Source is `src/main/resources/assets/icbmclassic/recipes/`. ## Integration review qualifications

Central registration, missile payloads, cluster manifests and targeting are integrated in the current tree. Missile save data validates finite start/lift and bounded target/time data. Payloads persist through entities and jobs; guided interceptor UUID/lifetime and EMP zones persist separately. Flight now includes persisted high-altitude simulation/reentry and bounded optional temporary tickets; no permanent forced chunks are used. Alpha.4 client effects use ordinary Minecraft render layers and synchronized flight/machine state; the full-pack client visual check covered redmatter and selected machine/weapon models. Multiplayer rendering/UI and shader-pack appearance still need testing. The integration review identified armed-cart recovery duplication, tier range bypass and spectator defuser checks. Current source contains fixes for all three: armed/triggered carts detonate without recovery, target validation uses the base range, and the defuser rejects spectators. Final regression-test results belong in the integrating agent's validation record.

## Release gates

1. Keep every implementation row tied to actual target sources and evidence; mark approximations and intentionally unavailable integrations explicitly.
2. Compile common/client sources and remap the production artifact; validate port metadata and ensure no restricted upstream resources are included.
3. Run meaningful unit tests for pure simulation/targeting/serialization and dedicated server GameTests for registration, each payload family, delivery form, machine, persistence, configuration and invalid networking.
4. Playtest client rendering/screens/audio, two-player synchronization, chunk/world restart, long-range simulation, automation, defense interoperability and blast performance under representative settings. Record actual results, not intended tests.
5. Verify survival progression: obtain resources, craft machines and payloads, charge/configure, launch, detect/intercept, detonate/defuse and recover persisted world state. Creative-only item availability is not survival parity.

Until these gates and per-row acceptance criteria are demonstrated, this remains an incomplete Fabric reimplementation of ICBM Classic.
